# TitanTPP — PAKDD 실험 보강 1·2·3 설계 결과

**현재 기준선 — 완료 결과 재사용**

대표 모델은 `titantpp_history_mlp`다. 네 데이터·외부6모델·3seed의 현재 validation 비교 84조건과 selected checkpoint 준비, Core·RAF·추가TPP 감사, MAC 대비 효율 측정을 재사용한다. 현재 원고와 기존 결과 수치는 바꾸지 않았다.

이번 작업은 원고의 세 질문을 실험으로 확인하기 위한 준비다: 평가가 개발 과정과 얼마나 분리됐는가, 이력 보완이 단순 용량 증가 이상의 역할을 하는가, 간헐 수요를 직접 다루는 방법과 비교해도 유용한가.

| 단계 | 이번에 확정한 내용 | 남은 부분 |
|---|---|---|
| 1. 평가 데이터 성격 | 연구자 답변 “기억이 불확실함”을 기록. 기존 test는 과거 노출 불확실 split으로 분류 | 미사용 독립 모집단은 확보·확정되지 않음 |
| 2. 구조 비교 | 같은 파라미터 수의 현재 상태 MLP, 직전 사건이 있으면 모든 분기를 쓰는 MLP. 24조건 설계 | 실제 통합 모델·학습 구현 |
| 3. 직접 비교군 | Deep Renewal native 분포를 유지한 다음 사건 adapter. 12조건 설계, 네 데이터 지원 범위 확인 | PyTorch 이식·native 대조·실행 비용 검증 |

**1. 평가 데이터 사용 경로를 정한다 — 분류 완료 / 독립 모집단은 외부 작업 대기**

[평가 데이터 결정](evaluation_population.md)에 기존 test를 사용하는 경로와 미사용 데이터를 확보하는 경로를 구분했다. 과거 test 산출물이 있다는 사실만으로 실제 선택 사용을 단정하지 않고, 기억이 불확실하다는 답변으로 미사용을 확인했다고 쓰지도 않는다. 과거 manifest의 목표 분포 요약 노출 기록도 함께 보존했다.

기존 test의 평가 가치는 유지되지만, ‘한 번도 보지 않은 독립 test’라는 보장은 하지 않는다. 추가 validation 개발이 끝난 뒤 전체 비교 목록과 지표를 잠그고 평가한다. 독립 확인을 추가하려면 실제 미사용 기간/외부 데이터의 계보를 먼저 확보해야 한다. 기존 행을 재분할해서 새로운 독립성을 만들지는 않는다.

**2. 이력 보완의 두 대안을 계산식으로 고정한다 — 설계·CPU 참조 검증 완료**

[구조 비교 설계](architecture_controls.md)는 두 대안의 입력, mask, 파라미터, 초기화, 잔차 위치를 고정한다. 현재 상태 대안은 폭6으로 **기준선과 같은 6,144개 파라미터**를 갖는다. 모든 분기 대안은 같은 직전 상태를 읽으며 **고정 /8**을 유지한다. 기존 활성 분기 정규화 실험과 혼동하지 않는다.

범위는 두 모델 × 네 데이터 × 세 seed의 **24개 신규 조건**이다. 대표 MLP 12조건은 재사용한다. 기존 보완 없는 B는 세 데이터 9조건만 있어 RAF까지 완료된 비교로 표기하지 않는다.

**3. 직접 수요 비교군을 선정하고 데이터 적합성을 확인한다 — 설계·지원 범위 검증 완료**

[Deep Renewal 설계](direct_baseline.md)는 원 논문과 고정 GluonTS source를 대조해 interval–size LSTM, shifted negative binomial head, 수량 평균 예측을 유지하도록 정했다. 네 데이터 × 세 seed의 **12개 신규 조건**이다. 마지막 수량과 같은 window의 평균 수량도 비학습 기준으로 추가한다.

train·validation에서 수량의 정수 지원 범위와 실제 target 수를 확인했다. 첫 사건의 gap0은 기존 loader 규칙을 그대로 따르며, Instacart의 기록값30은 tail 확률로 처리한다. Deep Renewal의 native NLL을 보존하므로 여섯 공통 head 비교군과 목적이 다르다. 원 논문의 달력 수요 예측 전체 재현으로 표현하지 않는다. FlexTPP는 원문·연결 구현 검토 후 후순위로 기록했다.

**검증과 산출물 — 완료**

- [CPU 검사](test_design.py): **18개 통과**. 실제 동결 MLP와 수식 일치, 동일 추가 파라미터, 초기 잔차·RNG, 인과성, 마스크 경계, 올바른 predecessor, NB 모수화와 top-code 식을 확인했다. full model/CUDA qualification과는 구별한다.
- [자료 지원 범위](data_support.json): 네 데이터의 train·validation만 대상으로 확인했다. 데이터 파일 SHA를 원래 manifest와 대조했다.
- [설계 계약](design_contract.json)·[36조건 목록](proposed_run_matrix.csv): `design_fixed_non_executable`로 기록했다. 실제 실행 Runtime·비용·마감·launcher는 아직 없다.
- [평가 성격 결정](evaluation_population_decision.json)·[원문 및 코드 근거](sources.json)·[검증 기록](verification.json)을 함께 남긴다. 원고·기존 과학 source·과거 감사 기록의 SHA를 보존했다.

GPU 학습, 새로운 성능 측정, held-out 성능 열람, 원격 제어, 스케줄 생성, commit/push는 수행하지 않았다. CPU 검사는 수식과 설계를 확인하는 것이며 모델의 성능 향상을 입증하는 결과는 아니다.

**남은 작업 순서**

1. **구조 비교와 Deep Renewal을 실제 학습 코드에 연결한다 — 다음 작업.** 로컬 `paper_research`의 기존 변경을 보존하고 별도 모델 identity·adapter를 구현한다. initialization·padding·target pairing·top-code tail·checkpoint 저장/복구 검증까지 마치면 실행 계약을 작성할 수 있다.
2. **실측 자원에 맞춰 GPU 실행 계약을 확정한다 — 다음 작업 / 실제 GPU 실행은 승인 필요.** 5080에 Taxi·Intermittent·RAF, 5090에 Instacart를 배치하는 안을 검토한다. 현재 자원 상태와 비용을 확인하기 전에는 실행 예약이나 ETA로 제시하지 않는다. 기존 캠페인의 마감·예산을 자동으로 이어받지 않는다.
3. **추가 validation 실험과 분석으로 주장 범위를 확정한다 — 이후 작업.** 전체36조건의 성공·실패와 같은 seed 비교를 보존한다. 결과에 따라 이력 보완의 필요성 및 적용 범위를 원고에 반영한다.
4. **최종 평가 모집단과 모델을 잠근 뒤 평가한다 — 이후 작업 / 독립 데이터는 외부 작업 대기.** 미사용 데이터를 확보하면 별도 계보를 확정한다. 기존 test를 쓰는 경우 과거 노출 불확실성을 공개한 reserved-split 평가로 남긴다. 전체 평가 실행·열람 계약을 승인받은 뒤 한 번 수행한다.
5. **최종 결과를 Experiments·초록·결론에 반영한다 — 이후 작업.** 개발 결과와 최종 평가 결과를 구분하고, 확인된 범위에서 기여를 정리한다.

평가 계보 확보와 별도 모델 구현은 병행 가능하다. 공통 loader·checkpoint 규약·최종 모집단에 의존하는 통합 검증과 실제 실행은 순서대로 진행한다.
